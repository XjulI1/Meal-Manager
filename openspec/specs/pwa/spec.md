## Requirements
### Requirement: Web App Manifest

The system SHALL serve a web app manifest at `GET /manifest.webmanifest` with
`Content-Type: application/manifest+json`, describing the application so that
browsers offer to install it.

The manifest MUST declare: `name`, `short_name`, `display: "standalone"`,
`start_url: "/"`, `scope: "/"`, `theme_color`, `background_color`, `lang: "fr-FR"`,
and an `icons` array.

The `icons` array MUST include at least a 192×192 and a 512×512 PNG icon, plus a
512×512 icon with `purpose: "maskable"` for adaptive Android masking.

#### Scenario: Manifest is served and parses
- WHEN a client requests `GET /manifest.webmanifest`
- THEN the response is `200 OK`
- AND the `Content-Type` is `application/manifest+json`
- AND the body parses as JSON with `display == "standalone"` and `start_url == "/"`

#### Scenario: Manifest advertises installable icons
- WHEN the manifest is fetched
- THEN `icons` contains an entry with `sizes == "192x192"` and `type == "image/png"`
- AND `icons` contains an entry with `sizes == "512x512"` and `type == "image/png"`
- AND `icons` contains an entry with `purpose == "maskable"`

#### Scenario: Referenced icon files are present
- WHEN the manifest lists an icon `src`
- THEN that icon file exists under the served static root (`public/`)
- AND it is a valid PNG of the declared dimensions

### Requirement: Manifest link injected client-side (SPA)

Because the application is a SPA (`ssr: false`), the system SHALL inject the
`<link rel="manifest">` into the document head at runtime via the
`<VitePwaManifest />` component mounted in `app.vue`. Static manifest links in the
build-time head config are intentionally NOT used (the PWA module strips them to
manage the link itself, which would otherwise drop the tag).

The document head SHALL also carry, in the static shell, a `theme-color` meta and
the Apple PWA metas/links (`apple-touch-icon`, `apple-mobile-web-app-capable`,
`apple-mobile-web-app-title`) so iOS "Add to Home Screen" renders correctly.

#### Scenario: theme-color and apple icon are in the static shell
- WHEN the SPA shell HTML is requested
- THEN the head contains a `<meta name="theme-color">`
- AND the head contains a `<link rel="apple-touch-icon">`

#### Scenario: VitePwaManifest is mounted
- WHEN `app.vue` renders
- THEN `<VitePwaManifest />` is present in the component tree (it adds `<link rel="manifest">` to the DOM after hydration)

### Requirement: Service worker precaches the app shell

The system SHALL register a service worker (generated by `@vite-pwa/nuxt` /
Workbox) that precaches the application shell assets (JS, CSS, HTML, icons,
fonts). The service worker SHALL use `registerType: "autoUpdate"` and a
navigation fallback to `/` so client-side routes resolve from the cached shell.

The service worker MUST be available at `GET /sw.js` after a production build.

#### Scenario: Service worker is produced by the build
- WHEN the application is built (`pnpm build`)
- THEN `sw.js` and a `workbox-*.js` runtime are emitted to the static output
- AND requesting `GET /sw.js` returns `200` with a JavaScript content type

### Requirement: Dynamic data is never served stale (no data offline)

The service worker SHALL NOT cache dynamic endpoints. Requests whose path starts
with `/api/`, `/mcp`, or `/.well-known/` MUST be excluded from the navigation
fallback and MUST NOT be served from cache, so household data is always fetched
from the network. Full offline operation of data is explicitly out of scope.

#### Scenario: API paths are excluded from the navigation fallback
- WHEN the PWA navigation fallback is configured
- THEN its denylist excludes paths matching `/^\/api\//`, `/^\/mcp/`, and `/^\/\.well-known\//`

### Requirement: Install and update prompts

The system SHALL present a discreet, dismissible install prompt when the browser
fires `beforeinstallprompt` (and the app is not already installed), and a
"new version available" notification when an updated service worker is waiting.

The update reload MUST be triggered by an explicit user action (not an automatic
silent reload), to avoid discarding in-progress form input.

#### Scenario: Install prompt appears when installable
- GIVEN the app is not already installed
- WHEN the browser signals the app is installable (`$pwa.showInstallPrompt`)
- THEN an install affordance is shown that calls `$pwa.install()` on confirm
- AND a dismiss action calls `$pwa.cancelInstall()`

#### Scenario: Update prompt requires user confirmation
- WHEN a new service worker is ready (`$pwa.needRefresh`)
- THEN a "reload to update" affordance is shown
- AND it calls `$pwa.updateServiceWorker()` only when the user confirms
